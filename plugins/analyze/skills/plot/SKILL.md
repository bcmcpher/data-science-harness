# Skill: plot

Produce figures **from files that exist**, as a provenanced step, so that every panel can be traced
to the output it was drawn from.

> Figures are generated by a script that runs like any other analysis: written to `code/`, executed
> through `analyze/run-comparison` so the figure's inputs and outputs are recorded. A figure that
> was made by hand and dropped into the repository has no provenance, and is the usual reason a
> panel cannot be regenerated six months later.

## When to use
- A comparison has produced outputs and they need to be seen — exploratory, during the work.
- A kept comparison needs publication figures: consistent theme, readable at print size, labelled
  axes and units.
- Do NOT use when the analysis has not run — there is nothing to plot. Do NOT use to interpret what
  the figure shows, or to choose which results are worth showing; both are the researcher's.

## Steps

1. **Locate the outputs to plot** — the comparison branch and the actual result files under
   `derivatives/cmp-<slug>/`. If the expected outputs are absent, stop and say so: the analysis has
   not been run (`analyze/run-comparison`), or it failed.
2. **Ask what the figure is for.** Exploratory (fast, disposable, no styling budget) and publication
   (fixed size, embedded fonts, colourblind-safe palette, vector format) have different requirements
   and the answer changes the script.
3. **Agree the figure's content** with the user: which variables on which axes, which grouping, what
   the error bars represent, and what is being claimed. Ask what the error bars are rather than
   choosing; SD, SE and a 95% CI look identical and mean different things.
4. **Write the figure script** to `code/fig-<slug>.<ext>`. It reads the result files, and only the
   result files, and writes to `derivatives/cmp-<slug>/figures/`. Apply project-wide styling if the
   project already has a plotting style; otherwise propose one and keep it in one place so figures
   stay consistent across comparisons.
5. **Run it under provenance** — route to `analyze/run-comparison` with the result files as `-i` and
   the figure directory as `-o`, so the figure carries the same record as the analysis.
6. **Log it** — append one entry to `project.yaml`:
   `{ ts, op: plot, stage: analyze, note: "figures <paths> from <output files>", branch: cmp/<slug> }`.
7. **Save** — delegate to the **datalad doer**:
   > "save: `datalad save -m 'plot: figures for cmp/<slug>'`."
8. **Report** — each figure, the output file it was drawn from, and what it does and does not show.

## Constraints

- **Every value on a figure comes from a produced output file.** No recalled numbers, no
  illustrative data, no "example" points, no axis limits chosen to imply a range the data do not
  cover. If a series is missing, the figure is missing it too.
- **Never produce a mock-up, sample or placeholder figure.** A plausible-looking chart is
  indistinguishable from a real one at a glance and will be presented as a result. If the data are
  not there, say what is missing instead of drawing something.
- **Never annotate a figure with a statistic that was not read from an output** — no significance
  stars, no p-value, no n, no effect size unless the analysis wrote it to a file.
- **Do not interpret.** The figure caption describes what is plotted and where it came from; whether
  it supports a conclusion is the researcher's call.
- Do not silently drop points, clip outliers, transform an axis, or exclude a group. If any of those
  is wanted, it is a choice to be stated in the caption and the log.
- Keep `log:` append-only and the ledger schema-valid; delegate the save to the datalad doer.
